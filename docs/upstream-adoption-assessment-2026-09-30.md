## 建议

## 双引擎的收益与成本

值得考虑它的理由不只在于“多一个 Codex”：

1. **长任务配置更稳定。** 当前 `httpapi/stock_research.go` 在请求前后检查当前模型身份，研究期间切换模型会返回“研究期间模型配置发生变化”。上游通过 `agent.BindTask` 冻结任务的引擎、模型、密钥及 Skill 配置，让旧任务继续用启动时的设置执行；个股与持仓等子任务可以沿用同一快照。
2. **设置保存失败更容易保持一致。** `appsettings.Store.UpdatePrepared` 与运行配置准备/回滚协调，减少“文件已变化但设置未激活”的不一致。上游有配置回滚测试，这不是跨文件数据库事务。
3. **后续 AI 功能有统一入口。** 对话、个股、持仓、复盘不需要分别理解引擎。准备扩展 AI 任务时，这个边界有维护价值。
4. **模型能力更明确。** Responses 原生能力检测、模型目录和思考档位有针对性的处理，避免把某个模型的档位套用到其他模型。

相应成本：

- 包含新增适配器及大批包名/接口迁移，影响所有 AI 调用路径；功能范围明显大于解决两处冲突。
- 需要下载/校验应用内 Codex 0.159.0，增加开发环境、打包资源与原生进程验证工作。上游默认桌面开发入口会准备两个 Runtime，即使默认引擎仍是 Hermes。
- Codex 要求实际模型服务支持原生 Responses；只支持 Chat Completions/Messages 时继续用 Hermes。代码不会静默转换模型协议或切换引擎。
- 应用设置自己的 `CODEX_HOME`、`HOME` 和 `USERPROFILE`，不会自动复用本机 Codex 的登录与配置。安装新引擎本身不会免去项目模型连接配置。
- 聊天历史沿用并迁移会话标识；切换引擎用可见历史重建原生会话，不等于迁移完整的隐式记忆和推理状态。
- 本机现有模型密钥尚未配置，这次无法确认你将使用的供应商是否满足 Responses 和工具请求兼容要求。未做真实模型或原生双引擎验收，不能将源码测试存在当作本机验证通过。

**建议定位：第二阶段的 AI 基座升级。** 若近期确定会扩展 AI 研究/持仓/复盘任务，提前整组同步是合理的；若近期只修改行情功能，延后不会阻塞当前工作。

- 如要清理工作台顶部栏，直接采用最终行为，不单独重演 `a07af29`。

这是按功能移植，未必逐个原样 cherry-pick。以后正常合并上游时仍需要核对这些已移植行为，避免重复或样式覆盖；分阶段的收益是当前改动较小，代价是后续还会进行一次集成。

### 第二阶段：确认 AI 路线后同步双引擎

一旦决定采用，建议从当前 fork 的独立开发分支正常合并最终 `df5d57f` / `v1.3.0`，保留本地功能与双方历史，整体接入公共 Agent Service 及 Windows MCP 修复。默认仍可用 Hermes，不要求日常一定切到 Codex。

同时同步本地 `scripts/dev-windows.ps1` 的 Runtime 准备；上游默认 npm 脚本仍使用 POSIX 环境变量/构建写法，不应替换已准备好的原生 Windows 入口。检查已移植 UI、报告/聊天兼容和本地 Windows 测试；完成后端、前端、桌面及双 Runtime 原生验证，再使用实际配置验收模型连接。

### 第三阶段：有安装器/发布需求时处理发布改进

届时纳入 `9c8aaed` 和适用的平台打包修复，调整 fork 的版本命名及更新源。当前 `desktop/update-feed.cjs` 默认仍指向原作者 OSS，这是仓库已有配置，不是本次新增；自定义发行前应避免后续更新覆盖二开版本。
